Hellmaker

Custom C++ game engine - Team Infernumb

Hellmaker is the in-house engine that ships Death's Refrain. It is a team-built C++ stack: a static library (Hellmaker Engine), an ImGui editor executable, and a Sandbox / game executable. I was Design Lead, and I also wrote engine-side debugging plus a large share of the editor's Dear ImGui UI. Technical lead / engine champion was Loh Boon Cheong, Timothy.

Debugger

I implemented Hellmaker's global debug tools: log levels (trace through critical), output targets (console, file, or both), a ring buffer so we could keep the last N messages, initialize/terminate, and crash helpers with a custom reason. Logging sits on spdlog and is shared by Engine, Editor, and Sandbox, so a gameplay bug and an editor bug hit the same pipeline.

On the editor side I built the Debug Console system: an ImGui window that pulls those logs in real time so designers and programmers could filter what the engine was actually doing without attaching a separate logger.

ImGui editor

I owned the editor GUI render manager: wrapping ImGui so the rest of the editor could draw without leaking ImGui types everywhere, then driving the window layout. I also wrote the asset browser (with Timothy as co-author) so we could pick files through ImGuiFileDialog, and contributed to the game view. That tooling is why level iteration was an editor problem instead of a rebuild-the-game problem.

Why it mattered for design

A custom engine is only useful to a designer if iteration is possible. Hellmaker exposes GameObjects with transform, sprite, and collider components, plus Lua state machines (onEnter / onUpdate / onExit, persistent context). Levels and scenes are data (YAML maps and scenes), not hard-coded rooms. The editor can toggle editor mode, show FPS, and jump back to a project launcher. That is the pipeline I used to place tiles, hazards, tutorials, and encounters without treating every layout as an engine feature request.

Gameplay systems that look like "design" still have engine contracts: turn-based input, line of sight for attacks, dialogue and video playback, scene switching with a fader, audio through FMOD. If those contracts are late or unclear, level design stalls. My job was to keep mechanics and spaces aligned with what the engine could actually run.

Technical overview (team)

C++20-class codebase, CMake (Debug / Release / Shipment). Windowing via GLFW. Audio via FMOD. Scripting via Lua state machines on logic components. Editor UI via Dear ImGui, with gizmos and file dialogs. There is also an in-engine web dashboard for live stats and controls. Engine systems include render, audio, fonts/textures, input, logic, dialogue, video playback, and delayed scene switching.

Solution split: Engine (library) / Editor (tooling) / Sandbox (the game). That split is why Death's Refrain can be a content project on top of a reusable runtime.
